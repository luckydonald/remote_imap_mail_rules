# remote_imap_mail_rules

Runs mail rules via IMAP, independent of the provider.
Python 3.14+ with `uv`, async throughout; run tests with `uv run pytest`.
Follow `/code-style`; `.env` and `.env.example` are blocked for agents, so `.example-env` is the documented template.
All stages of `ai/initial.md` are built.

## Layout

- `src/remote_imap_mail_rules/rules/`: `models.py` (pydantic rule file), `fields.py` (field and operator enums), `values.py` (dates), `extract.py` (field to mail mapping), `operators.py`, `evaluate.py`, `loader.py`, `schema.py`. Fields are `Templatable` (a value or a `Var`) and `Template` expressions are resolved by `.concrete()` in `loader.py`, see Templates below.
- `src/remote_imap_mail_rules/imap/`: `client.py` (`ImapClient`: read-only `EXAMINE` / `BODY.PEEK`, plus the write methods `select`, `store_flags`, `move`, `delete`, `append`; `fetch_raw` reads a whole mail with `BODY.PEEK[]`, `find_message_id` searches by `Message-ID`), `watcher.py` (IDLE or polling), `fetch.py` / `sexpr.py` / `bodystructure.py` (response parsing), `connection.py` (the slice of `aioimaplib` used, so tests can fake it), `utf7.py` / `transfer.py` (folder names and part decoding for the mail browser). `ImapClient` also has `folder_counts`, `list_page`, `fetch_message` and `fetch_part` for the browser.

## Decisions

- Reading IMAP is read-only: `EXAMINE` and `BODY.PEEK`. Writes exist only as the actions of rules, through `ImapClient.store_flags` / `move` / `delete` / `append` (a real `SELECT`, `UID MOVE`, else `COPY` + `\Deleted` + `UID EXPUNGE` of that one UID, refused without `UIDPLUS`), and only when `ACTIONS_ENABLED=true` (default false, then the server never writes to a mailbox). The mail browser has two user-driven write routes under the same gate, `POST /api/mail/accounts/{id}/messages/{uid}/flags` (only `\Seen`, `\Flagged`, `\Answered`) and `.../move` (same account, 409 `actions_disabled` when off); the Watcher logs them as `user_action`, since `OwnChanges` only knows rule actions. Reading in the browser stays `EXAMINE` / `BODY.PEEK`, and opening a mail never marks it read.
- Accounts are referenced by a UUID (`IMAP_ACCOUNT_ID`, `account_id` in rules), never by name, because names can change. The id can be set when adding an account and edited in the UI so two systems share it: `PUT /api/accounts/{id}` with a new `id` rewrites the old UUID as text in the stored rules (`replace_account_id`, file or database, comments stay), and `mail_events` follow by `ON UPDATE CASCADE` (migration 0005). `seed_from_env` skips seeding when a stored account is identical to the environment's (host, port, ssl, username, password) under another id. `IMAP_ACCOUNT_NAME` is a display label only.
- A rule has several `locations` (`account_id`, `folder` default `INBOX`, `recursive` default false), so equal rules for several inboxes need no duplicates. Recursive folders are expanded once at start-up via `LIST`; missing folders are skipped with a warning.
- Env vars are unprefixed (`IMAP_HOST`, ...). Only automated tests use the `TEST_` prefix, via `tests/settings.py`, and they never read `.env`.
- One connection and task per folder, because IDLE blocks its connection. Headers, flags, size and `BODYSTRUCTURE` are fetched up front, bodies lazily and only when a rule needs `body_text` / `body_html`.
- Change detection: IDLE push when the server has it (renewed before 29 minutes), else polling every `IMAP_POLL_INTERVAL`. New mails by UID, flag changes via `CONDSTORE` `CHANGEDSINCE` when available, a changed `UIDVALIDITY` reloads the folder.
- A field that does not exist makes every operator false, even negating ones like `ne`. Only `presence` with `value: false` and the `not` combinator can express absence. `body_text` never falls back to `body_html`.
- Dates are a discriminated union on the bool `relative`: `AbsoluteTime` (datetime, naive means UTC) or `RelativeDuration` (`7d`, units `s m h d w`, measured back from now). `date_received lt 7d` means received more than a week ago. There is no `age` field, a relative duration replaces it.
- IMAP has no last-modified date; `modseq` is only a change counter (CONDSTORE).
- Folder names are used as the server sends them (modified UTF-7), not decoded.
- A rule's folder uses `/` for subfolders and is resolved to the server's real name by `ImapClient.resolve_folder` (delimiter, `INBOX.` namespace prefix, case ignored) for moves, appends and location expansion; a name the server lists is kept as is.
- Templates: root `templates` holds definitions (`type: template`, `defaults`, `content` with `{var: name}` / `!var name` markers). A use is `<<: *anchor` plus `variables`, valid wherever an expression is, checked by pydantic (every variable bound, none unknown). `parse_rules` returns `.concrete()` rules, so evaluator and matching never see a `Var` or `Template`: the models are generic in `V = Var` (`Templatable[T, V] = T | V`), `.concrete()` returns the `[Never]` form (`RuleFile[Never]`, `Rule[Never]`, `Expression[Never]`, where `T | Never` is just `T`), and consumers annotate with that form. YAML anchors may not contain `.`.
- The server edits only the file at `RULES_PATH` (file mode), or the database when it is unset (database mode); the client never sends a path. `PUT` validates with `parse_rules` first (422 with messages, file untouched) and replaces the file atomically. Files opened in the editor never write to disk.
- Accounts live in the database (`DATABASE_URL`, default SQLite, Alembic migrations run at server start). Passwords are Fernet-encrypted with `SECRET_KEY`, never returned by the API. The env account is seeded once and never overwritten, a difference is only reported (`env_differs`, field names only).
- Database mode stores one row per rule and per template as the non-concrete dump, so `Var` and template uses survive, but YAML comments and anchors do not. A rule keeps its row id across saves by name.
- Error reporting (Sentry SDK, works with Bugsink): `SENTRY_DSN` (backend) and `VITE_SENTRY_DSN` (frontend, another project) are both empty by default, then nothing is initialised. The `VITE_` name is only the `bugsink-setup` skill's convention: the server reads it at runtime and gives it to the browser through `GET /api/public/client-config` (`frontend/src/sentry.ts` fetches it after the app is mounted), so no build bakes it in. There is no tunnel, the browser posts to the DSN host itself. Release is `SENTRY_RELEASE`, else `SOURCE_COMMIT` (Coolify), else git, else `unknown`; the frontend's falls back to the backend's. `init_sentry` runs in `main()` before `create_app`, and the lifespan reports a failing start-up (migration) before re-raising. `/sample-error` (frontend, unlinked) and `GET /api/sample-error` raise on purpose.
- Git for the rules folder: the git folder is `settings.git_dir` (`RULES_DIR`, default `DATA_DIR/rules`, or the folder of `RULES_PATH` in file mode). In database mode `DatabaseRulesStore.write_mirror` writes `rules.yml` there after every save and at start-up (the non-concrete dump, no comments). `GitRepo` runs the `git` binary (no shell, one lock, `GIT_CONFIG_GLOBAL=/dev/null`, `-c safe.directory`), credentials only via the environment of the one process (`GIT_ASKPASS` helper in `DATA_DIR/git/` for HTTPS, `GIT_SSH_COMMAND` with the generated ed25519 key in `DATA_DIR/git/ssh/`), messages scrubbed of the token. Settings are the single row `git_settings` (token Fernet-encrypted, write-only in the API). `GitService.auto` runs after a rules save (background task): commit if enabled and auto-commit and the repo is initialised (init is always manual), then push if auto-push; it never raises, errors land in `last_error`. Auto-push needs auto-commit, a rejected push is an error, no force and no pull. `tests/conftest.py` points `DATA_DIR` at a temp dir so tests never write `./data`. The container keeps everything in `/data` (`DATA_DIR`, `DATABASE_URL`) and ships `git` and `openssh-client`.
- Login gates all of `/api` except `/api/auth/*` and `/api/public/*` (`require_login` is set per router in `create_app`). Only the admin unlocks it (`ADMIN_USERNAME` / `ADMIN_PASSWORD`, on Coolify the magic variables `SERVICE_USER_ADMIN` / `SERVICE_PASSWORD_ADMIN`; the mail accounts' credentials do not), compared in constant time, a failed login pauses 0.5 s. The session is a Fernet token of `SECRET_KEY` in an HttpOnly cookie holding an HMAC of the admin login, so changing either variable ends all sessions; without the key or the admin variables the login and the gated routes answer 503. The `IMAP_*` seed account is optional (`env_ignore_empty`). `fetchConfig()` in the frontend returns `'login'` for 401 / 503, `null` still means file-only mode.
- The mail browser opens one IMAP connection per request (`imap_session`, factory on `app.state.imap_factory` so tests use `FakeServer`), the folder is a query parameter, paging uses a `before_uid` cursor. Mail HTML is sanitized with `nh3` (remote images dropped, `cid:` rewritten to the part URL) and shown in an iframe sandboxed without `allow-scripts`; parts other than a few image types and PDF are forced to download with a `sandbox` CSP.
- Actions (`actions.py`): per mail, rules are processed in file order and the first matching rule wins. `plan_steps` expands its actions into steps (`noop` where the mail is already as wanted, only the first `move`, a move always last, a move to another account is a normal move step). If the winner changed the mail, the rules are evaluated again from the top on the in-memory `Mail` (flags updated, no refetch); a move, an error or an all-`noop` winner ends the pass, a rule runs once per pass. A `Writer` decides what steps do: `ImapWriter` (own connection of an `ActionRunner`, never the `IDLE` ones; the mail is fetched fresh first) or `VirtualWriter` (dry run). The `Watcher` queues one `Act` per mail after its first match when `actions_enabled` and writes one `action` event per `done` / `error` / `skipped` step (`detail` `{type, status, reason?, folder? / keyword?, value?}`, under the source key); `noop` steps are not logged. A move to another account (`ImapWriter.move_across`) skips the copy if the target folder already has the `Message-ID`, else `fetch_raw` + `APPEND` with the flags and date, and only then deletes the original at the source (`UID EXPUNGE`, needs `UIDPLUS`), so a failure leaves a duplicate and never loses the mail; a failed delete is an `error` step `source_not_deleted`. Other accounts' clients come from `ActionRunner.target` through a `SettingsLookup` (`Watcher.lookup_settings`), an unknown account is `unknown_account`. After a move with a known new UID (`COPYUID` / `APPENDUID`, needs `UIDPLUS`) the `Watcher` writes a `moved_in` `action` entry under the target key (`detail.from` has the old account, folder and uid), the target folder's watcher still logs `first_seen` there and `message_id` links both. `Watcher.allow_move` refuses the sixth move of one `Message-ID` (`MAX_MOVES`) as `move_loop`, so rules cannot ping-pong a mail.
- Dry run (`dry_run.py`, `server/api/dry_run.py`, `DryRunPanel.vue`): `POST /api/dry-run` `{rule, yaml?}` runs the whole rule file's chain with the `VirtualWriter` over the rule's folders in pages (`limit` mails looked at, default 200, newest first; the stateless `cursor` / `next` is `{account_id, folder, before_uid}`) and answers the summary and affected mails of that page with their chains; the panel adds the pages up, fetches on by itself when a page has no affected mail and shows "Load more…" otherwise; it never writes to a mailbox or the log, and takes the editor's unsaved YAML. `POST /api/dry-run/run` applies the saved rule like the watcher and writes the `action` events, 409 `actions_disabled` while `ACTIONS_ENABLED` is off. `GET /api/editor/config` carries `actions_enabled`, the panel disables Run now with a hint when it is off or the rule is unsaved.
- Action log: table `mail_events` (`kind` `first_seen` / `rule_match` / `action` / `user_action`), a mail is `(account_id, folder, uidvalidity, uid)` with `message_id` kept; `Mail.uidvalidity` is set by `ImapClient.build_mail`. The `Watcher` (started in the `create_app` lifespan unless `WATCH_ENABLED=false`, which the tests set) logs `first_seen` via `matches(on_inspect=...)` and `rule_match` per match (`existing` only once, `new` / `changed` every time) and restarts, as a background task after the commit, on account create / update / delete and on a rules save. `action` is written by the actions, `user_action` by the user-change detection (next entry). SQLite foreign keys are switched on per connection so `ON DELETE CASCADE` works. The frontend keeps the log of the open mail in `useMailStore().events` (not persisted) and shows it in `MailLog.vue`.
- Action log screen (`/log`, `ActionLogView.vue`, `log-api.ts`): `GET /api/log/events` lists newest first with the filters `account_id`, `folder`, `kind` (repeatable), `rule`, `since`, `until` and `q` (case insensitive over rule name, folder, `Message-ID` and the detail as text), paged by the opaque cursor `before` (`created_at|id`, so equal instants are not skipped; index `ix_mail_events_created_at`, migration 0006), times answered as UTC. `GET /api/log/status` has `last_change` (newest `first_seen` / `rule_match` / `user_action`) and `last_action` from the database, and `last_run` from `Watcher.last_run`, which is in memory only (set by the `on_poll` callback of `matches()` on every IDLE push or poll wake-up), so it is `null` after a restart until the first one. `next_run` is the earliest planned poll and `push` says some folder waits in IDLE (no planned time); both come from `Watcher.due`, filled by the `on_schedule` callback of `matches()` / `watch()` (a poll time before each sleep, `None` before IDLE), in memory only. The screen keeps its filters in the URL query.
- User actions: `matches(on_change=...)` reports `FlagChange` (new `Mail`, old flags; also for mails no rule matches) and `MailGone` (`ImapClient.list_uids` against the snapshot `load_existing` keeps per folder, looked at when `HIGHESTMODSEQ` moved, every poll without `CONDSTORE`). The first load and a `UIDVALIDITY` reload are the baseline and report nothing. The `Watcher` writes `user_action` `{type: "flags", added, removed}` (`\Recent` ignored) or `{type: "gone"}` (moved or deleted, not told apart). `OwnChanges` keeps its own doing out, decided when the change is noticed: while a mail's rules run everything on it is ours, afterwards the flags the chain ended with (once) and a move are remembered.
- Fill from mail: the editor has an "Example mail" side panel (a subpage on a phone) that reuses the mail browser. A condition's "From mail" button and "+ Add condition" take their value from `useMailStore().context` (the open mail, `null` offline), and the address part follows the condition's `part`. The editor shows the mail it fills from as a chip (`MailChip.vue`, top of `RuleEditor.vue`); its × sets `useMailStore().fillDetached`, so the editor's consumers (`ConditionNode`, `GroupEditor`, `TextLikeEditor`) use `fillContext` (null then) while the mail screens keep `context`, and opening another mail attaches again. The `in` operator takes all values, otherwise the first. In the normal editor a new condition type starts filled from the open mail, and changing an address condition's field or part refills it in one undo step (`changeAddress`) unless the value was typed by hand. The `Rule ▾` > "Add to existing rule" dialog can also add a template use (`templateUseFor`): each variable is filled from the leaf of the template's content it is the `value` of, using that leaf's own field, header name and address part, and a variable no leaf can fill is left out so the default applies. `GET /api/mail/.../messages/{uid}` also returns all headers, flags, keywords and the other address headers for this. Pinia stores are used directly with `useX()` in every file that needs them, no provide/inject for global state: `useStore` (`model/store.ts`, the rule editor's document, a setup store so refs are unwrapped: `store.view`, not `store.view.value`), `useMailStore` and `usePrefsStore`; only the per-subtree `ALLOW_VARS` flag is still an injection key.

## Rule expressions

Rule file: `rules:` list of `name`, `enabled` (default true), `locations`, `when`, `actions`. The `when` tree is a discriminated union on `type`:

- Combinators: `all` and `any` (`conditions`, at least one), `not` (`condition`). Nest freely.
- `text`: `field`, `operator`, `value`, `case_sensitive` (default false, valid for every operator), `quantifier`.
- `address`: like `text` plus `part` (`full`, `name`, `address` (default), `local_part`, `domain`).
- `header`: like `text` but with a header `name` instead of a field, for custom headers.
- `number`: `field`, `operator`, `value` (a `[low, high]` pair for `between`), `quantifier`.
- `date`: `field`, `operator`, `value` (`TimeValue`, or a pair for `between`).
- `bool`: `field`, `value` (default true), `quantifier`.
- `presence`: exactly one of `field` / `header`, `operator` `exists` (default) or `empty`, `value` (default true).

Operators:

- text: `equals`, `contains`, `startswith`, `endswith`, `regex` (search), `glob`, `in` (value is a list).
- number and date: `eq`, `ne`, `lt`, `gt`, `gte`, `lte`, `between` (inclusive).
- Quantifier for multi-valued fields: `any` (default), `all`, `none`. No values at all counts as missing, so false.

Fields and where they come from:

| Type | Fields | Source |
|---|---|---|
| text | `account_id`, `folder` | location / fetch context |
| text | `subject`, `message_id`, `in_reply_to`, `references`, `list_id`, `auto_submitted`, `precedence`, `importance` | headers (RFC 2047 decoded) |
| text | `body_text`, `body_html` | `text/plain` / `text/html` parts, lazy; a missing part is a missing field |
| text | `mime_type`, `keywords` | top `BODYSTRUCTURE` type, flags minus system flags |
| text | `auth_spf`, `auth_dkim`, `auth_dmarc` | `Authentication-Results` |
| text | `attachment_mime_type`, `attachment_filename`, `attachment_extension` | `BODYSTRUCTURE`, one value per attachment |
| address | `from`, `sender`, `reply_to` (`Reply-To`), `return_path`, `to`, `cc`, `bcc`, `recipients` (to+cc+bcc), `delivered_to` | headers; `in_reply_to` is separate from `reply_to` |
| number | `size` | `RFC822.SIZE` |
| number | `spam_score` | first of `X-Spam-Score`, `X-Rspamd-Score`, `X-Spam-Status` (`score=`), `X-Spam-Level` (star count) |
| number | `attachments_count`, `attachment_size`, `uid`, `modseq` | `BODYSTRUCTURE` / fetch |
| date | `date_sent` | `Date:` header |
| date | `date_received` | `INTERNALDATE` |
| bool | `seen`, `flagged`, `answered`, `draft`, `deleted` | `FLAGS` |
| bool | `spam_flag` | `X-Spam-Flag`, else `X-Spam-Status` starting with `Yes` |
| bool | `is_reply`, `has_list_unsubscribe`, `attachment_inline` | `In-Reply-To` / `References`, `List-Unsubscribe`, `BODYSTRUCTURE` |

Actions (run when `ACTIONS_ENABLED`, see Decisions): `move` (`folder`, optional `account_id`), `mark_read`, `mark_unread`, `flag`, `keyword`.

To add a field: extend the enum in `rules/fields.py`, map it in `rules/extract.py`, then regenerate the schema and add a test case in `tests/test_rules_evaluate.py`.

- Mail view (`MailMessage.vue`): `.mail-message` is the one scroll column (header, blocked images, iframe, log), the iframe is sized to `body.scrollHeight` by a `ResizeObserver` and has `overflow:hidden`. The header toolbar (not in the compact side panel) has mark read/unread, `MailMoveMenu` (move targets of the rules' `move` actions for this account first, `More …` opens `MailFolderTree`, a real tree with synthetic parents, arrow keys and a filter), `MailRuleMenu` (new rule from the mail, or add a condition to any group of an existing rule through `appendCondition(when, added, path)` / `groupsOf`, `path` undefined keeps the old top-level behaviour) and the `SegmentedToggle` `[ Text | HTML ]`. The menus use `.menu-pop`, anchored at the button's left edge; the `Rule ▾` one adds `.end` (right edge) because the scrolling `.mail-message` column clips whatever sticks out of it. Their dialogs (`.modal-backdrop`) are `<Teleport to="body">`, because Safari on an iPad clips a fixed dialog to the scrolling pane that holds it (seen on a real iPad; Playwright's WebKit is a desktop build and does not, so `mail.spec.ts` checks that the backdrop is a child of `body` and that no ancestor clips). View settings live in `usePrefsStore` (localStorage, screen `/settings`): `bodyMode` (default html), `remoteImages` and `mailStyles` (`block` default / `allow`).
- Mail HTML policy: `sanitize_html(html, part_url, allow_remote, allow_styles)` returns `Sanitized` with `html`, `blocked_images` (remote URLs left out, listed above the mail as `a.innerText == a.href`), `broken_embeds` (`cid:` without a part) and `styles_blocked`. `cid:` lookup is case-insensitive, `data:image/(png|jpeg|gif|webp)` is kept, other `data:` / `cid:` URLs are dropped outside `img src`. Remote images and CSS are off unless `GET .../messages/{uid}?remote_images=true&styles=true`; allowed CSS is filtered (no `@import`, scripted values, off-site `url()`, `position: fixed`). `frameDocument()` adds a CSP meta (`default-src 'none'; img-src 'self' data:`, plus `https: http:` when remote images are on) as the second layer, so blocking is intended and not a CORS accident. The iframe has no `allow-scripts`, console messages "Blocked script execution in 'about:srcdoc'" with an unknown source are not from the app. Not built yet: rule-based auto-allow (`remote_image_rules` in the rule file, plan stage 8).
